## Findings

### F-INT-01 — HIGH (owner-raised) — AI spend cap undercounts past 5,000 events/day — FIXED
`supabase/functions/_shared/spend.ts` (PR #19): the gate summed `ai_events` fetched with `.limit(5000)` ordered ascending — past 5,000 events (and past PostgREST's own row cap) the sum covered only the oldest rows, so the cap stopped binding exactly when spend was highest. **Fix:** migration `0044_ai_spend_ledger.sql` — per-user/day ledger updated by one atomic upsert RPC (`charge_ai_spend`, service-role only, RLS on with no client policies); the gate reads the single-row total, denies at/over cap, and pre-charges a worst-case estimate per request (`estimateWorstCaseChargeUsd`; chat 7 calls, ask 1, extract 3 attempts). The events sum survives as `sumSpendFromEvents()` (reporting only), now fully paginated via `.range()`. **Proofs:** concurrency — 20 parallel `charge_ai_spend` × $0.10 on real Postgres → total exactly 2.000000, one row, no lost increments; unit regressions — gate binds with an EMPTY events table, charge/read RPC errors deny (fail-closed), 6,000-event paginated sum is exact where the truncated read undercounts; scratch — 0044 applied + privileges verified. Residual bound (documented in spend.ts): concurrent in-flight requests can push the LEDGER past the cap by at most their combined worst-case charges; actual provider spend stays below the ledger. **Note:** PR #19's own branch still contains the superseded implementation — if the owner merges PR-by-PR instead of using this integration, #19 must be amended with 0044 + the new spend.ts first (or the integration branch used as the merge vehicle). **CI catch (integration PR #36, first run 38333777995):** the rls-audit job flagged `ai_spend_daily` as a zero-policy table — by design (deny-by-default system table). The audit's own mechanism for this class is its SYSTEM_TABLES allowlist; `ai_spend_daily` was added to it with a rationale comment (permissive policies would WEAKEN the posture). rls-audit + authz-behavioral verified ALL GREEN locally after the change. This is recorded because it is exactly the kind of combination-only failure this audit exists to catch.

**Owner final correction (same day) — authorize+charge unified, estimates made defensible.** Two residual concerns were raised against the first fix and both were upheld on inspection: (1) the gate still decided on a READ and then charged (two operations, a boundary race); (2) the per-request charge used a flat 2,000-token input allowance that nothing enforced. Corrections:
- **One atomic operation:** `charge_ai_spend` is replaced by `try_charge_ai_spend(user, day, amount, cap) -> total | NULL` — a single upsert whose UPDATE carries the cap predicate under the row lock (plus an explicit `amount > cap` guard for the INSERT branch and invalid-input rejection). The ledger can now NEVER exceed the cap: charges land fully under it or not at all. **Real-Postgres race proof, wired into CI** (`supabase/tests/spend-ledger-check.mjs`, rls-audit job): 50 parallel charges of $0.10 against a $2.05 cap → exactly 20 succeed, 30 rejected, final total EXACTLY 2.000000; oversized first charge and invalid inputs rejected; verified locally before push.
- **Measured per-attempt charges:** the per-request pre-charge is gone. Every model-call ATTEMPT is charged at its seam (chat `callModel`/`callVision`, ask's attempt loop, extract's attempt loop, and memory-learn — an AI path the original PR #19 scope missed) with `chargeModelCall`, priced from the attempt's own assembled payload: input = payload chars × 0.75 tok/char bound (+2,000 tokens per image), output = the call's hard `max_tokens`, all at the table's maximum rate so provider fallback chains can never out-price the charge. Retries re-enter the seam and are charged as the real second requests they are. `checkSpendCap` is now a read-only pre-check (fail fast, charges nothing). Missing/non-finite/negative estimates deny WITHOUT an RPC (unit-pinned).
- **Charged-path inventory:** chat (model + vision), ask, extract, memory-learn are charged. `transcribe` is NOT token-charged: it is a per-audio-minute Whisper call on Groq's free tier, rate-limited (10/min, 100/hr), with no token telemetry — recorded here as a deliberate exclusion for the owner's awareness, not an oversight.
- **CI-wiring caveat (infrastructure, not code):** `spend-ledger-check.mjs` is in the branch and green locally, but the 4-line ci.yml step that would run it in the rls-audit job could NOT be pushed: GitHub requires the Workflows permission for ref updates touching `.github/workflows/*`, and the connector token doesn't carry it (403 on ref update; the identical push without ci.yml succeeded immediately). Owner options: widen the token's Workflows permission, or apply the step from the local branch state. Until then the concurrency proof is local-evidence only — stated plainly so the CI claim is never overstated.
- Superseded text above (the read+charge description and the 7/1/3-call charges) is retained as the round-1 record; this addendum is the current state.

### F-INT-06 — LOW — deliberate fail-open rate limiter (documented trade-off) — NOTED
`_shared/rate-limit.ts` bumps counters through the atomic `bump_rate_limit` RPC (no read-then-write race) but fails OPEN on counter errors by design (a broken counter store must not take chat offline). In combination this is acceptable because the spend ledger (F-INT-01 fix) fails CLOSED independently — spend stays bounded even if rate limiting is degraded. Recorded so the posture is a decision, not an accident.

### F-INT-07 — LOW — fire-and-forget extraction chaining can silently miss — NOTED (pre-existing)
`transcribe/index.ts:155` and `chat/index.ts:224` chain to `extract` with `.catch(() => {})`. If the chain call fails, the note remains unextracted (its transcript is intact and extraction is re-runnable — no data loss), but nothing retries it. Follow-up candidate: a retry/queue (also covers the D8 runbook's known gap). Extract's own item-insert fallback (index.ts:317) was inspected: it degrades ONLY on column-missing errors naming the column and rethrows everything else — not a swallowed-error defect.

### F-INT-08 — INFORMATIONAL — bounded working sets are product limits, not truncations
