## Findings

### F-INT-01 — HIGH (owner-raised) — AI spend cap undercounts past 5,000 events/day — FIXED
`supabase/functions/_shared/spend.ts` (PR #19): the gate summed `ai_events` fetched with `.limit(5000)` ordered ascending — past 5,000 events (and past PostgREST's own row cap) the sum covered only the oldest rows, so the cap stopped binding exactly when spend was highest. **Fix:** migration `0044_ai_spend_ledger.sql` — per-user/day ledger updated by one atomic upsert RPC (`charge_ai_spend`, service-role only, RLS on with no client policies); the gate reads the single-row total, denies at/over cap, and pre-charges a worst-case estimate per request (`estimateWorstCaseChargeUsd`; chat 7 calls, ask 1, extract 3 attempts). The events sum survives as `sumSpendFromEvents()` (reporting only), now fully paginated via `.range()`. **Proofs:** concurrency — 20 parallel `charge_ai_spend` × $0.10 on real Postgres → total exactly 2.000000, one row, no lost increments; unit regressions — gate binds with an EMPTY events table, charge/read RPC errors deny (fail-closed), 6,000-event paginated sum is exact where the truncated read undercounts; scratch — 0044 applied + privileges verified. Residual bound (documented in spend.ts): concurrent in-flight requests can push the LEDGER past the cap by at most their combined worst-case charges; actual provider spend stays below the ledger. **Note:** PR #19's own branch still contains the superseded implementation — if the owner merges PR-by-PR instead of using this integration, #19 must be amended with 0044 + the new spend.ts first (or the integration branch used as the merge vehicle). **CI catch (integration PR #36, first run 38333777995):** the rls-audit job flagged `ai_spend_daily` as a zero-policy table — by design (deny-by-default system table). The audit's own mechanism for this class is its SYSTEM_TABLES allowlist; `ai_spend_daily` was added to it with a rationale comment (permissive policies would WEAKEN the posture). rls-audit + authz-behavioral verified ALL GREEN locally after the change. This is recorded because it is exactly the kind of combination-only failure this audit exists to catch.

**Owner final correction (same day) — authorize+charge unified, estimates made defensible.** Two residual concerns were raised against the first fix and both were upheld on inspection: (1) the gate still decided on a READ and then charged (two operations, a boundary race); (2) the per-request charge used a flat 2,000-token input allowance that nothing enforced. Corrections:
- **One atomic operation:** `charge_ai_spend` is replaced by `try_charge_ai_spend(user, day, amount, cap) -> total | NULL` — a single upsert whose UPDATE carries the cap predicate under the row lock (plus an explicit `amount > cap` guard for the INSERT branch and invalid-input rejection). The ledger can now NEVER exceed the cap: charges land fully under it or not at all. **Real-Postgres race proof, wired into CI** (`supabase/tests/spend-ledger-check.mjs`, rls-audit job): 50 parallel charges of $0.10 against a $2.05 cap → exactly 20 succeed, 30 rejected, final total EXACTLY 2.000000; oversized first charge and invalid inputs rejected; verified locally before push.
- **Measured per-attempt charges:** the per-request pre-charge is gone. Every model-call ATTEMPT is charged at its seam (chat `callModel`/`callVision`, ask's attempt loop, extract's attempt loop, and memory-learn — an AI path the original PR #19 scope missed) with `chargeModelCall`, priced from the attempt's own assembled payload: input = payload chars × 0.75 tok/char bound (+2,000 tokens per image), output = the call's hard `max_tokens`, all at the table's maximum rate so provider fallback chains can never out-price the charge. Retries re-enter the seam and are charged as the real second requests they are. `checkSpendCap` is now a read-only pre-check (fail fast, charges nothing). Missing/non-finite/negative estimates deny WITHOUT an RPC (unit-pinned).
- **Charged-path inventory:** chat (model + vision), ask, extract, memory-learn are charged. `transcribe` is NOT token-charged: it is a per-audio-minute Whisper call on Groq's free tier, rate-limited (10/min, 100/hr), with no token telemetry — recorded here as a deliberate exclusion for the owner's awareness, not an oversight.
- **Re-review correction (round 2):** the independent re-review of head `3f68768` returned **FAIL, narrowly scoped** — the two corrections above passed outright, but the inventory was incomplete: `route` and `classify` (user-triggerable model calls, `max_tokens: 200`, auth-gated + rate-limited since PR #18) were uncharged and undisclosed, and `memory-consolidate`'s per-user episode call was likewise absent. All three are now charged at their seams (route degrades to its deterministic defaults on denial; classify returns the 429 cap response; consolidate charges per user inside its episode call). The reviewer also caught that `callVision`'s own try/catch swallowed its `__SPEND_CAP__` throw as a null result — fixed to rethrow, so the call site's cap mapping is reachable. A guard test now pins the inventory: every function file that calls a model endpoint must reference `chargeModelCall`, with transcribe the sole exception. **The inventory is now exhaustive by construction: 7 of 8 model-calling functions charge the ledger; transcribe is the only exclusion.**
- **CI-wiring caveat (infrastructure, not code):** `spend-ledger-check.mjs` is in the branch and green locally, but the 4-line ci.yml step that would run it in the rls-audit job could NOT be pushed: GitHub requires the Workflows permission for ref updates touching `.github/workflows/*`, and the connector token doesn't carry it (403 on ref update; the identical push without ci.yml succeeded immediately). Owner options: widen the token's Workflows permission, or apply the step from the local branch state. Until then the concurrency proof is local-evidence only — stated plainly so the CI claim is never overstated.
- **Owner arrangement (final validation round):** the complete workflow change is prepared as a standalone owner-approvable artifact — `docs/autonomous/audit/CI_SPEND_LEDGER_STEP.md` (exact step, unified diff, two application routes via the owner's own account, verification instructions). No broader credentials were requested. Applying it is a one-minute owner action whenever they choose.

**Cost-bound validation (final round) — the estimates are now proven bounds, and two real violations were found and fixed.** The owner rejected `TOKENS_PER_CHAR_BOUND = 0.75` and `IMAGE_TOKEN_BOUND = 2000` as unproven estimates. Full inventory + validation:
- **Supported models (complete, from `_shared/ai.ts`):** the deployment runs ONE provider config chosen by env — OpenAI (`gpt-5-mini` text, `gpt-4o-mini` vision) or Groq (`openai/gpt-oss-120b` text, `qwen/qwen3.8-27b` vision). There is NO in-request cross-provider fallback in the code (the round-2 text implying fallback chains is corrected). Transcription: whisper-large-v3-turbo / gpt-4o-mini-transcribe (per-minute, excluded — see inventory).
- **Text bound — PROVEN by construction:** all four tokenizers are byte-level BPE, where encoding starts at one token per UTF-8 byte and merges only combine — so tokens ≤ bytes, always. The 0.75 factor is DELETED; seams now measure `inputBytes` (UTF-8 bytes via `TextEncoder`), plus a flat 96-token envelope allowance for chat-template framing (~18 messages × ~4 documented overhead tokens, with margin). The old factor genuinely undercounted dense scripts: Arabic runs ~2 bytes/char and up to ~1 token/char, so 0.75 tok/char could under-reserve Arabic-heavy payloads by ~25-60%.
- **Image bound — DERIVED from the provider's documented algorithm:** the vision call sends no `detail`, so provider defaults apply. OpenAI's published gpt-4o-mini accounting: base 2,833 + 5,667 per 512px tile, with the 2048px-fit + 768px-shortest-side geometry capping any image at 8 tiles = **48,169 tokens worst case** (a typical phone photo = 4 tiles = 25,501 — already 12.7× the old bound). Groq's vision docs cap image input at 2,048 tokens/image. `IMAGE_TOKEN_BOUND` is now **50,000** (OpenAI worst case rounded up). Per-image reservation at the max rate ≈ $0.04 of the $2 budget — the cap still binds; heavy vision users simply reach it sooner, which is the cap working as intended.
- **Pricing bound — a REAL violation found:** qwen/qwen3.8-27b's listed rates ($0.80 in / **$4.00 out** per 1M) EXCEED gpt-5-mini's ($0.25/$2.00) — the old claim "every chain member's rates are ≤ the fallback's" was FALSE for the Groq vision path (under-reservation up to $0.0008/vision call: small, but the claimed invariant did not hold). Also gpt-oss-120b's output rate is source-conflicted ($0.60 Groq page vs $0.75 reseller catalogs). Fixes: the rate table now carries qwen 0.80/4.00 and gpt-oss output at the higher 0.75; `FALLBACK_RATE` is DERIVED as the component-wise table maximum; a negative unit test asserts the fallback dominates EVERY table entry, so a future pricier model raises the charging rate automatically instead of breaking the bound silently.
- **Output bound:** unchanged and hard — each call's enforced `max_tokens`/`max_completion_tokens` (chat 2000, vision 400, ask/extract 1200, memory-learn 500, route/classify 200, consolidate 400); on the GPT-5/gpt-oss paths the cap includes reasoning tokens.
- **Claims corrected (requirement: stop claiming guaranteed containment):** the ledger guarantee is exact and unconditional — **the ledger total can never exceed the cap** (enforced by the RPC). Containment of ACTUAL provider billing is CONDITIONAL on the bounds above holding at the providers' stated formulas/rates. Earlier phrasings ("the ledger therefore always ≥ the actual provider spend", "can never out-price") are superseded by this section wherever they appear in round-1/2 text and in code comments (the spend.ts header now states the conditional scope verbatim).
- **Residual risks (exact):** (1) a provider reprices or changes its image preprocessing/tokenizer without notice — bounds are only as durable as the published formulas; (2) an extreme-aspect-ratio image if OpenAI's implementation upscales beyond the documented geometry (no documented evidence; phone photos are 4-6 tiles); (3) a future model/config change to a non-byte-level tokenizer would void the byte argument — the inventory guard + dominance test catch rate/table drift, but a tokenizer-family change needs a human review trigger (noted in the watch item); (4) qwen's rates rest on Groq's model listing as reported in research (preview model, not independently re-verified against a logged-in console); (5) transcribe remains per-minute and outside the token ledger (disclosed exclusion).
- **Safe operational limit (proposed, owner-approved values unchanged):** keep the provisional $2.00/day cap and the `AI_SPEND_CAP_OFF=1` kill switch; ADD a daily reconciliation control — compare `sumSpendFromEvents` (actual-token costing at table rates) against the day's ledger reservations per user and raise an ops alert if actuals exceed reservations for any user/day (that inequality is the tripwire that a bound has broken in production). The reconciliation is specified here, not yet automated — automating it is a small follow-up the owner can schedule; until then, the reservation-side cap binds regardless, and worst-case provider overshoot per vision call is bounded by the 48,169-token derivation (~$0.012 at qwen output rates for the completion side plus input at $0.80/1M ≈ $0.039/call absolute worst case).
- Superseded text above (the read+charge description and the 7/1/3-call charges) is retained as the round-1 record; this addendum is the current state.
